前端项目 AGENTS.md 编写模板

AGENTS.md 是什么

AGENTS.md 是写给 AI 编程代理的项目协作说明。它不描述某一个具体需求，而是告诉代理在这个项目中应该如何理解代码、执行命令、修改文件和验证结果。

一份好的 AGENTS.md 应该让代理快速回答以下问题：

  • 这个项目使用什么技术栈？
  • 重要代码和配置分别在哪里？
  • 如何安装、启动、测试和构建项目？
  • 修改代码时有哪些约束？
  • 哪些文件不能直接修改？
  • 任务完成前必须执行哪些检查？

实现规则

通用规则

  • 优先复用已有组件、工具函数、类型定义和请求封装。
  • 修改前先搜索现有实现，避免创建重复逻辑。
  • 保持现有目录结构和命名风格，不要为了小改动大范围重构。
  • 新增公共函数或组件时，使用清晰、稳定的参数和返回值类型。
  • 不要为了简单功能引入新的依赖。

TypeScript 规则

  • 优先使用明确的类型定义，避免无必要的 any。
  • 不要通过关闭 TypeScript 检查来掩盖类型错误。
  • 修改公共类型后，检查所有使用方和相关测试。

组件规则

  • 组件应尽量保持单一职责。
  • 页面专用组件放在页面对应目录，跨页面复用的组件放在公共组件目录。
  • 组件的输入、输出和事件命名遵循项目现有约定。
  • 处理加载、空数据、错误和禁用状态，避免只实现成功状态。

样式规则

  • 优先复用项目已有的设计变量、组件样式和响应式断点。
  • 不要随意引入全局样式或覆盖第三方组件的全局行为。
  • 新增页面时，至少检查桌面端和移动端布局。
  • 不要使用无法解释的魔法数字；必要时提取为变量或设计 token。

API 与状态管理规则

  • API 请求统一通过项目现有请求层处理。
  • 不要在多个组件中重复实现同一份请求逻辑。
  • 修改接口数据结构时，同步更新类型、状态管理和页面展示。
  • 对加载中、请求失败和空结果提供明确的用户反馈。

测试与验证

  • 新增功能必须补充对应测试。
  • 修复 bug 时，先添加可以复现问题的测试，再修改实现。
  • 修改组件后，至少验证正常状态、加载状态、空状态和错误状态。
  • 修改路由、权限或接口类型后，检查所有相关调用方。
  • 完成修改后运行与本次变更相关的 lint、测试和构建命令。
  • 如果某项检查无法运行，必须在最终说明中写明失败原因。

生成文件与敏感文件

  • 不要直接修改 dist/、coverage/、.cache/ 等生成目录。
  • 不要提交 .env、私钥、访问令牌、密码或其他敏感信息。
  • 修改依赖时，只使用项目指定的包管理器更新 lockfile。
  • 不要手动删除或重建用户数据、数据库和生产配置。

Git 与变更边界

  • 未经明确要求，不要创建、修改或推送 Git commit。
  • 不要执行 git reset --hard、批量删除或其他不可逆操作。
  • 保持修改范围最小，只改动完成任务所必需的文件。
  • 如果发现与当前任务无关的已有修改，不要覆盖或回滚它们。

完成标准

任务完成前确认：

  • 实现符合现有架构和命名约定。
  • 相关测试已经新增或更新。
  • lint、测试和必要的构建检查已经执行。
  • 没有直接修改生成文件或提交敏感信息。
  • 用户可见行为发生变化时，相关文档已经同步更新。
  • 最终说明中列出修改内容和验证结果。

编写时的常见错误

规则过于空泛

“保持代码优雅”无法指导具体操作。应该说明目录、命令、命名方式或验收标准。

命令与项目实际情况不符

写入前检查 package.json、锁文件和 CI 配置，确认命令确实可以运行。

重复整个 README

README 负责介绍项目，AGENTS.md 负责说明代理如何安全地修改项目。两者可以互相引用，不必复制全部内容。

把一次性任务写进去

“这次把首页改成蓝色”属于具体任务，不应该长期放在 AGENTS.md 中。文件应主要记录稳定的项目规则。

规则互相矛盾

例如一处要求“所有组件使用 Options API”，另一处要求“所有新组件使用 Composition API”。遇到这类情况，应明确适用范围或删除过时规则。

最后检查清单

  • 文件放在项目根目录或正确的子目录。
  • 技术栈和目录说明与项目实际情况一致。
  • 所有命令都能在项目中找到对应脚本。
  • 规则具体、简短且可以验证。
  • 已说明测试、lint 和构建要求。
  • 已标注生成文件和敏感文件。
  • 没有写入密码、密钥或一次性任务。
  • 没有和其他项目文档、配置或子目录规则冲突。

一句话总结：AGENTS.md 不是“我要实现什么功能”，而是“在这个项目里，应该怎样安全、统一、可验证地完成任务”。
